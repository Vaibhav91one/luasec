# 730 untrusted data written into an HTTP header or URI

Severity: high · Confidence: high · CWE: CWE-93

## What it means

Request data reaches a call that writes it into the HTTP message:
`ngx.resp.set_header`, `ngx.req.set_header`, `ngx.req.set_uri`,
`ngx.req.set_uri_args`, `ngx.redirect`, or the assignment form
`ngx.header[k] = v`. That is the Lua surface of
[CVE-2020-36309](https://nvd.nist.gov/vuln/detail/CVE-2020-36309), which NVD
records as "unsafe characters in an argument when using the API to mutate a URI,
or a request or response header" in lua-nginx-module before 0.10.16. Before the
fix a CR or LF in the value was written out unescaped, so attacker-chosen bytes
can end a header line and start another one.

Which message the bytes land in is what differs between these sinks.
`ngx.resp.set_header` and `ngx.redirect` write the response the client parses, so
a CRLF splits one response into two. `ngx.req.set_header`, `ngx.req.set_uri` and
`ngx.req.set_uri_args` rewrite the request this handler forwards upstream, so the
CRLF lands on the upstream request. Same defect, same fix.

## The assignment form, and where the key is not

`ngx.header["Set-Cookie"] = token` is an assignment to an index target, not a
call, so it is a sink in a **target position** rather than a callee position.
It is still this code: the same value reaches the same response header and a CRLF
in it does the same thing. It is not a second number because a user filtering on
730 must see both spellings of one risk.

Two positions matter, and only one of them is the sink:

- **the value** (`= v`) is where untrusted data reaches the HTTP message. This is
  the sink, and it is what is reported. Confidence and severity are exactly the
  call form's, taken from the source descriptor rather than guessed at the shape.
- **the key** (`[k]`) is deliberately **out of scope**, and reported as nothing.

A tainted key is the attacker choosing *which* header is written while the program
still chooses the bytes in it. That is header selection, not CRLF injection, and
it is not what CWE-93 names. It is written down here rather than left undefined
because leaving it undefined is how the next reader assumes it is covered. It
also leaves no injection surface open on its own: where the value is tainted as
well, the value position still fires and covers the CRLF.

```lua
local name = ngx.req.get_uri_arg("name")
ngx.header[name] = "fixed"     -- not reported: the key picks the header name
ngx.header[name] = name       -- reported: the VALUE position is the sink
```

A constant assigned to `ngx.header` is not reported either, for the same reason a
constant `set_header` argument is not: every handler writes constants, so only a
proven taint flow is a finding.

NVD records no CWE for CVE-2020-36309 (`NVD-CWE-noinfo`), so CWE-93 is this
tool's judgement: it is the parent class for CRLF injection into any header or
URI, which is what the advisory text describes, and it covers the request-side
sinks as well as the response-side ones that CWE-113 alone would miss. Where the
write is a *response* header, CWE-113 is the more specific name for the same
defect and the consequence is a second response the client reads as part of the
first. A tainted `ngx.redirect` target has two readings and both are this
finding: a CRLF in it is the same injection, and an unvalidated host is an open
redirect.

NVD scores CVE-2020-36309 CVSS 3.1 **5.3 medium** (integrity low; no
confidentiality or availability impact). This code is registered `high` anyway,
which is a judgement and not a copy of that score: the finding is about the risk
class of writing request data into a CRLF-capable position, and in a
reverse-proxy deployment the request-side sinks poison the *upstream* request
rather than only the caller's own response. Lower it with
`--severity-threshold` where the deployment does not proxy.

This is reported only on a proven taint flow. Every one of these APIs takes a
value on every call, so a merely non-constant argument is not a finding: a
header written from a local variable holding `"application/json"` is silent.
The finding does not depend on the module version being old - a patched
lua-nginx-module is safe, and this code says the data flow exists, not that the
deployment is exploitable.

A tainted subrequest body or header is a different risk and is `731`.

## Example

A greeting handler echoes the `name` parameter into a response header:

```lua
local name = ngx.req.get_uri_arg("name")
ngx.resp.set_header("X-Echo", name)
```

The assignment form of the same write fires the same way:

```lua
local token = ngx.req.get_uri_arg("token")
ngx.header["Set-Cookie"] = token
```

Both fire under `--std openresty`.

## How to fix

Do not build a header value out of request data. Bind the value to a known-good
form and let the framework write a constant:

```lua
local name = ngx.req.get_uri_arg("name") or ""
name = name:gsub("[^\032-\126]", "")   -- keep printable ASCII only
ngx.resp.set_header("X-Echo", name)
```

For a value that must not be reflected at all, drop the header. For a rewritten
URI, `ngx.req.set_uri` takes a path: validate it against a known route table
rather than accepting the request's own value.
