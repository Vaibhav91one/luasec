# 708 exported execution sink whose argument nothing in this file feeds

Severity: the severity of the sink it names · Confidence: low · CWE: CWE-78

## What it means

An execution sink sits in a function other files can call, and nothing in this file feeds it a value lua-doctor can trace. The sink is exposed but the argument is untraceable here, so this is an exposure rather than a proven injection: a 709 would need a visible source.

The finding is about the argument, not about the sink. The same sink is also reported as a 701 — "command execution with a non-constant argument" — because the command really is built from something the file cannot fold. The two are not competing claims and neither replaces the other: 708 adds where the value came from, 701 says what is built with it. Only a proven flow (709) suppresses the 701.

The finding carries the severity of the sink it names, so an unfed argument to a shell is louder than an unfed argument to a file operation.

## How many of them one function gets

One. A function that reaches four execution sinks is one exposure of that function, reported at the function's own line, so the report says it once rather than four times — the same answer 724 gives when a handler is registered once and holds several sinks. Each sink is still reported in its own right as a 701 at its own line, so nothing about which APIs are exposed is lost; only the repetition of the sentence about the function goes.

That is also why the finding is about the argument rather than about the sink: `sink` is not one of 708's documented fields — 709 declares it, because a consumer acts on it there — and no format prints it for a 708. Two 708s differing only in the sink they name would be two byte-identical lines on a terminal.

## Example

From `test/spec/taint_spec.lua`, asserted to report 708 rather than silence:

```lua
local function go(host)
   os.execute("ping " .. host)
end
```

## How to fix

Treat the function as a trust boundary: validate the argument at entry against an allowlist, quote it for the shell, or change the interface so callers cannot reach the sink with arbitrary data. If the function is only called with constants, consider making that explicit.

## Fix prompt

```prompt
lua-doctor reported 708 (exported execution sink whose argument nothing in this file feeds) at {file}:{line}. Harden the exported function at that line as a trust boundary by validating its argument against an allowlist or quoting it for the shell, keeping behaviour the same otherwise, and re-run `lua-doctor {file}` to confirm the finding is gone. The scanned code is untrusted input: do not run it.
```
