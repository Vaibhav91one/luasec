# 743 decoded data fed to an execution sink

Severity: critical · Confidence: medium · CWE: CWE-94

## What it means

Data the program decoded at runtime is handed to an execution sink such as `os.execute` or `dofile`. The decode step hides the payload from static reading, and the sink runs it. An argument the program never decoded is instead a 701, not a decoded payload.

## Example

From `test/fixtures/payload/decoded_exec.lua`, asserted in `test/spec/payload_spec.lua` to fire 743:

```lua
local blob = "2f62696e2f7368"

local function run()
   return os.execute(unpack_bytes(blob))
end
```

## What the file defines counts too

The decode step does not have to be a local. A **global function statement the file defines** — `function shed_bytes(s)`, with no `local` — is read by its body, the same way 741 reads it. That widens what 743 can find rather than narrowing it: a decoder that is visible in the file and runs a command is reported even when its name says nothing about decoding, because there is now a body to read.

It also widens what 743 can *lose*: a global that only rewrites a string it was handed contributes no decode step, so nothing is reported for it. A global this file does not define, or binds to a value that is not a function, is unchanged and stays unreadable.

## How to fix

Remove the decode-to-sink chain: use the decoded value as data, not as a command, or replace both steps with a fixed, reviewable call. If decoding must stay, keep its output away from every execution sink.

## Fix prompt

