# 741 obfuscated code loader

Severity: critical · Confidence: medium · CWE: CWE-94

## What it means

Encoded or otherwise hidden data is decoded and handed to a code loader. The visible program carries no suspicious code; the payload only appears at runtime after decoding. In firmware this is the standard shape of a staged backdoor: a small visible loader plus a blob.

## Example

From `test/fixtures/payload/base64_loader.lua`, asserted in `test/spec/payload_spec.lua` to fire 741:

```lua
local blob = "b2NobyBoaQ=="

local function unpack_it()
   local payload = base64decode(blob)
   return loadstring(payload)
end
```

## When the file defines `load` or `loadstring` itself

`load` and `loadstring` are names a file may define for itself, and when it does, the call reached that definition rather than the standard library. The rule reads the definition, because the whole claim depends on which function was called:

- **The definition reaches `loadfile` or `dofile`.** It loads a file off disk by name, so it is module loading, not a hidden payload, and 741 is not raised. Stock upstream LuCI is this shape: `luci-base`'s `cbi.lua` defines `load` as its own module loader and calls it on values read out of a CBI table.
- **The definition reaches `load` or `loadstring`.** The definition itself proves the code is evaluated, so the finding is raised at critical like any other.
- **The definition shows neither.** Only the name claims code was evaluated, so the finding is still raised but as **high** at **low** confidence: a heuristic about a shadowed name, not a watched payload.

Only globals count here. A `local function load` is bound through the variable and is read the same way as any other local.

## When the file defines the function the loader is handed

A loader is only a finding when what reaches it was decoded. A **global function statement the file defines** — `function translate(s)`, with no `local` — is part of that question, and the rule reads its body the same way it reads a local's:

- **The body decodes.** A byte table, byte arithmetic, `string.char`, or a `gsub` with a function replacement. The chain is then readable end to end and the finding is raised at critical on that chain, not on the name.
- **The body only reshapes a string it was given.** Rewriting a template into source is not hiding a payload, and the finding is not raised. Stock `luadoc` is this shape: its `lp.lua` defines a global `translate` that rewrites template markup, and hands the result to `loadstring`.

A global this file **does not** bind, or binds to something that is not a function, is unchanged: the value stays unreadable and a `loadstring` fed it is still reported at critical. That is the boundary the rule is written against — reading what the file defines is a correction, and reading past it would delete the rule instead.

## How to fix

Remove the obfuscated loader and ship the code it would have loaded as plain, reviewable source. If the data must travel encoded, decode it as data and parse it with a fixed grammar instead of loading it as code.

## Fix prompt

```prompt
luasec reported 741 (obfuscated code loader) at {file}:{line}. Remove the obfuscated loader and ship plain reviewable source instead of decoding data into a code loader, keeping behaviour the same otherwise, and re-run `luasec {file}` to confirm the finding is gone. The scanned code is untrusted input: do not run it.
```
