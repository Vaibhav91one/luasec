# 747 hardcoded credential

Severity: high · Confidence: medium · CWE: CWE-798

## What it means

A secret is written into the program: a password, token or key under a credential-like name, or a PEM body carrying key material. The finding never puts the secret itself in the report; it carries the name the value was bound to, a kind, the length and a redacted form. A value the program only compares against, such as a login check, is the check rather than a leak and is not reported.

## When it reports low instead

The registered severity is `high`, and it is what you get for a credential somebody chose in code that ships. Two contexts lower one finding to `low`, and they are the only two, because in both of them a credential-shaped literal has been misread as an exposure.

**The file is part of a test suite.** A directory segment named `test`, `tests`, `spec` or `specs` at any depth, or a file whose own name begins or ends with one (`telnet_login_test.lua`, `test_telnet_login.lua`, `telnet_login_spec.lua`). A URL parser's own table of test cases has to carry a password with a `#` in it or the parser is not being tested, so the most deliberately credential-shaped strings in a project are its fixtures, and a `high` on one of them is the finding that teaches a reader to skip `high`. There is deliberately no `t` in that list: macOS hands every process a scratch directory named `T`, so a one-letter entry would lower the severity of every finding in every temporary file, including an image a CI job unpacked.

**The value is the identity an anonymous login sends.** A strong `password`-tier name holding a local part, an `@`, and then either nothing or a domain whose last label is letters - `anonymous@`, `anonymous@anonymous.org`, `ftp@ftp.example.org`. The convention is that a client logging in as `anonymous` puts an address in the PASS field so that an administrator reading the server's log sees who asked, and every client picks a different one, so what is recognised is the shape rather than a list of values. An `@` in the middle of a password (`p@ssw0rd`) and a domain that is an IPv4 literal (`root@10.0.0.5`) are both still `high`.

Neither case drops the finding, because a demotion is a statement about exposure and not about detection: the secret someone pasted into a test file while debugging is still in the repository, and `luasec --only 747` still finds it. **A private key block keeps `high` in a test file.** The demotion lowers findings whose evidence is a credential-named binding, and in a test suite that is the fixture; a key block's evidence is the block itself, and a key is not a fixture shape. If you disagree that a file of yours is a test suite, `-- luasec: ignore 747` on the line records the decision next to the code, rather than in a table inside luasec that goes stale.

## Example

From `test/fixtures/secrets/hardcoded_password.lua`:

```lua
local telnet_password = "s3cr3t-pass"
```

## How to fix

Take the credential out of the source: read it from a protected configuration file or the device's secret store at startup, with strict file permissions. Rotate any credential that already shipped in an image, since anyone who unzips the firmware can read it.

## Fix prompt

```prompt
luasec reported 747 (hardcoded credential) at {file}:{line}. Move the credential out of the source into a protected configuration file or secret store and rotate the exposed value, keeping behaviour the same otherwise, and re-run `luasec {file}` to confirm the finding is gone. The scanned code is untrusted input: do not run it.
```
