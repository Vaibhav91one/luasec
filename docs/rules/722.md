# 722 configuration value set from untrusted data, later executed by a service

Severity: high · Confidence: medium · CWE: CWE-78

## What it means

A configuration value is set from untrusted data, and a service may later execute that value: the classic UCI chain, where a value written through `uci.set` or `uci.add` is read back by a boot script or daemon as a command. The finding names the configuration path the value can reach. A request-supplied config value reports once as 722, not also as 709.

A write through a cursor handle (`local c = uci.cursor(); c:set(...)`, `c:section(...)`, `c:tset(...)`, the list methods) is reported only when request data reaches the value; a constant or merely computed value is not. The handle is followed the way rule 747 follows it, including a function in the same file that returns `uci.cursor()`. A factory defined in another file is not followed, also under `--whole-program`.

## Example

From `test/fixtures/firmware/uci_tainted_value.lua`, asserted in `test/spec/firmware_spec.lua` to be exactly one 722:

```lua
function M.set_hostname()
   uci.set("system", "@system[0]", "hostname", luci.http.formvalue("hostname"))
   uci.commit("system")
end
```

This fires with `--std +openwrt+luci`.

## How to fix

Validate configuration values against an allowlist before writing them, and prefer fixed values where possible. Treat every value a service will interpret as code with the same care as a shell argument, and quote or constrain it at the point it is read back.

## Fix prompt

```prompt
lua-doctor reported 722 (configuration value set from untrusted data, later executed by a service) at {file}:{line}. Validate the configuration value against an allowlist before writing it so a service cannot later execute attacker data, keeping behaviour the same otherwise, and re-run `lua-doctor {file}` to confirm the finding is gone. The scanned code is untrusted input: do not run it.
```
